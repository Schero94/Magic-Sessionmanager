# Privacy and dependency acceptance

Scope: source and tests for GeoIP data flows, external providers, privacy, dependency advisories and compatible remediation.

## Focused contract before implementation

The config defaults enable geolocation with `auto`; the settings store overrides static config. A store read failure currently preserves static defaults, so a stored opt-out can be lost and a public session IP can be sent to ipapi. Preserve all existing explicit settings when the store is readable. If it is unavailable, disable geolocation until the cached failure expires or the cache is invalidated. Existing strict-session fail-closed behavior stays intact; geofencing may block or allow according to its existing failure policy. No route, response envelope, admin, or provider contract changes. Test a throwing store with a fake fetch and test recovery after cache invalidation before implementation. No provider requests or real credentials.

Mapped IPv4 addresses can also use hexadecimal IPv6 notation. The current classifier only unwraps dotted decimal, so a mapped private address can reach the remote provider. Normalize equivalent mapped forms before applying the existing IPv4 classification. Keep public mapped addresses eligible for the explicitly selected provider and preserve the private-result shape. Regression tests must prove both paths with a fake fetch.

Equivalent expanded or zero-padded IPv6 loopback and unspecified addresses must remain local as well. Canonicalize for classification without changing the returned original IPv6 representation.

When `auto` falls back after a local reader failure, log only a fixed message. Reader error details may contain local paths or input data; they must not be interpolated into logs. Preserve the lookup result and fallback decision.

## Data flow and compatibility

- `server/src/config/index.js` defaults to `enableGeolocation: true`, `geoIpProvider: auto`, and 90 retention days. Static config is overridden by normalized saved settings, cached for 30 seconds. A settings-store failure now disables geolocation and enables strict session enforcement until cache expiry or invalidation. This can affect login decisions where geofencing is configured to fail closed.
- `auto` uses an existing local database first. Without one it sends the IP to `https://ipapi.co/{ip}/json/`; when a local lookup fails it also falls back unless `geoLookupFailureMode` is `block`. Explicit `ipapi` uses the remote provider; `local-mmdb` never falls back remotely; `disabled` or `enableGeolocation: false` prevents remote lookup. Invalid and locally classified addresses do not go to the provider through `getIpInfo`.
- Login bootstrap, session-list enrichment and the admin lookup route can initiate lookups. The ipapi in-memory cache holds successful IP-keyed results for 24 hours and failures for 5 minutes; expiry is lazy on access or eviction, not a guarantee of timed deletion. Session rows store IP and selected city, region, country and timezone fields. Cleanup targets inactive sessions older than the configured period, runs at most daily, and `-1` means forever. Revocation records have a separate lifecycle.
- README now documents the enabled `auto` default, IP transmission to ipapi.co, the local failure-mode exception, local-only and disabled options, and the separate authenticated MaxMind download. `node --test tests/readme-geoip-privacy.test.mjs` passes. No default or migration was changed. The Settings disclosure is owned by the UI leaf; its final integration status is separate.
- MaxMind updates use a separate authenticated download workflow. Opt-in email and webhook notifications can transmit user email, session IP and location; optional license creation sends admin identity and device/network metadata. Provider handling, disclosures and retention beyond this plugin are not verified here. These flows belong to other files/owners.
- `getIpapiIpInfo` is independently callable and does not itself classify private addresses or recheck effective settings; current source callers route through `getIpInfo`. Treat direct future use as unsafe unless guarded. The IP classifier is not a complete IANA special-purpose address registry; review additional non-public ranges separately.

### Production advisory follow-up, 2026-11-06

The two high audit entries are two affected package nodes, not two independent CVEs. The underlying advisory is [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5), for constrained-collection memory exhaustion in Zod versions below 4.6.6. Reachability and exploitability through this plugin or a particular host have not been established.

`npm ls @strapi/utils zod --all --omit=dev` resolves the plugin peer `@strapi/utils@5.61.0` to its exact dependency `zod@4.4.3`. The plugin imports `@strapi/utils` for error classes in `server/src/policies/session-required.js`; Strapi core also directly requires the same version. The registry reports `@strapi/utils@5.61.0` as latest stable 5.x and pins Zod to `4.4.3`; 5.60.0 and 5.58.0 also pin `4.4.3`. `zod@4.6.6` and `4.6.7` are available, with 4.6.7 tagged latest. Adding a direct newer Zod dependency does not satisfy or replace the exact nested version. npm's proposed `@strapi/utils@4.26.2` is outside the plugin's Strapi 5 peer contract.

An isolated experiment in `/tmp/sessionmanager-zod-check.dH4zJt`, separate from the shared symlink, installed packages sequentially with `--ignore-scripts --no-audit --no-fund`:

- Baseline fixture with `@strapi/utils@5.61.0`: `npm ls` showed Zod 4.4.3; `npm audit --omit=dev` reported two high package entries.
- Root-override fixture scoped `@strapi/utils` to `zod@4.6.7`: `npm ls` showed the override; that minimal fixture's production audit returned zero findings. A simple error-class and bounded-array smoke test passed on both versions. This is not a full Strapi or plugin compatibility test and does not establish that a host override is safe for production.
- A separately packed synthetic plugin declared the same override plus a Strapi-utils peer; its consumer installed `@strapi/utils@5.61.0` and the fixture plugin. `npm ls` and a Node assertion confirmed the consumer still resolved Zod 4.4.3. The consumer audit showed the vulnerable chain. This verifies that a plugin-local override does not fix the consuming application's dependency tree, consistent with [npm package.json overrides documentation](https://github.com/npm/cli/blob/v10.9.9/docs/lib/content/configuring-npm/package-json.md#overrides).

Conclusion: no plugin-only change shown here fixes downstream hosts safely. The upstream blocker is Strapi 5's exact Zod pin; a Strapi 5 release that adopts a patched Zod version must be tested and incorporated, or each host owner may independently evaluate a root override with the complete host's dependency audit, build, integration and regression tests. We did not change the plugin's peer range, package metadata or lockfile, force a version, modify a host, or claim the host-override smoke test proves compatibility. The two plugin-lockfile audit entries remain open until a verified host-resolved fix exists.

### Isolated Strapi host override experiment, 2026-11-06

Created `/tmp/strapi-zod-host.jGtavR` with a fresh independent `node_modules`, SQLite database and a copied snapshot of this plugin's source. The fixture uses Strapi and Users & Permissions 5.61.0, Node 22.23.1, npm 10.9.8, and the scoped root override `{ "@strapi/utils": { "zod": "4.6.7" } }`. It is not a clone of the shared host or its complete plugin graph. Plugin build ran in the copy only. Config used synthetic fixture secrets, disabled GeoIP/webhooks/email alerts, and a preload guard rejected non-loopback socket connections during build, startup and validation. No provider calls were attempted intentionally. npm installation and audit used the registry; no provider credentials or real user records were used.

- `npm install --no-audit --no-fund`: passed in the fixture; `npm ls --all --omit=dev`: exit 0. `npm ls @strapi/utils zod --all --omit=dev` and Node `createRequire` confirmed Zod 4.6.7 for `@strapi/utils`, but Zod 4.4.3 remained in Strapi core/admin and other packages, and Zod 3.25.76 remained under `koa-body` and `koa-session`.
- `npm audit --omit=dev --json`: 37 affected package entries, 2 low, 18 moderate, 17 high, 0 critical. The original `@strapi/utils` finding no longer appeared for this override, but Zod GHSA-mrhx-c7xc-m3w5 remained in three nodes: root Zod and the two nested Zod 3 copies. This scoped override does not make the host audit clean. The host is a different dependency graph from the plugin audit, so totals are not comparable.
- Copied plugin `npm run build`: passed. Host `NODE_OPTIONS='--require ./network-guard.cjs' STRAPI_TELEMETRY_DISABLED=true npm run build`: passed. The first start failed because this minimal fixture lacked `public/uploads`; after creating that directory, guarded `NODE_ENV=development npm run start` started and plugin bootstrap completed. Loopback checks returned `/_health` 204, `/admin/` 200, and unauthenticated `/magic-sessionmanager/sessions` 401. A favicon request logged 500 because the fixture had no `favicon.png`; this is a fixture completeness defect, not a clean-console pass. The server was stopped normally.
- `node validate-fixture.cjs` with the network guard passed: Strapi `validateZodSchema` accepted valid input, returned Strapi `ValidationError` for three invalid patched-Zod inputs, and converted an error from a schema made with the separate root Zod 4.4.3 copy. A separate guarded Strapi Document Service script passed a synthetic valid create and four invalid cases (short required string, out-of-range integer, invalid enum, missing required string). This tests representative validation only, not the complete Strapi suite or a denial-of-service reproduction.

These checks show limited compatibility of the scoped override with this fixture, not production safety. Full Strapi and plugin regressions, actual target-host version/dependency graph, authenticated UI/API workflows, native and legacy session behavior, production-mode startup, multi-database cases, performance, complete Zod 3/4 paths and a final full-host audit remain unverified. Do not recommend deploying the override as proven safe. No plugin/host package metadata or lockfile in the workspace was changed, and no existing host was restarted or modified. Reference: [Strapi SQLite configuration](https://docs.strapi.io/cms/configurations/database).
